# AI 협업 자동화 파이프라인 — 설계 문서

- 작성일: 2026-11-26
- 상태: 초안 (사용자 승인 전)
- 표기: **[사용자]** = 사용자가 직접 정한 것, **[제안]** = 대화에서 제안했고 사용자가 동의한 것, **[판단]** = 설계자(Claude)가 정한 것으로 사용자가 검토할 대상

---

## 1. 의도와 이유

사용자는 그동안 개발, 퍼블리싱, 가끔 디자인까지 혼자 해 왔고 협업 도구(특히 깃헙)를 거의 쓰지 않았다. 최근 채용 등에서 "AI 활용 능력"을 많이 보고, 업계 협업 방식이 "AI가 일하고 사람은 정해진 지점에서 승인하는 구조"로 가고 있다고 판단했다. **[사용자]**

그래서 이 구조를 직접 만들어 보면서 익히고, **포트폴리오로 보여 줄 수 있게** 만드는 것이 목적이다. **[사용자]**

- 이 프로젝트의 주인공은 앱이 아니라 **앱 주변에서 돌아가는 자동화 흐름**이다. 앱은 연습용으로 새로 만들고 일부러 단순하게 잡는다. **[제안]**
- 혼자 하는 개발자에게 맞는 협업 구조다. AI가 동료 개발자 역할을 맡고, 사용자는 요청, 리뷰, 승인을 맡는다. **[제안]**

### 성공의 모습 **[제안]**

처음 보는 사람(채용 담당자 등)이 README와 짧은 시연 영상만 보고도 다음을 이해한다.
"이슈 하나가 AI 작업, 자동 검증, 사람 승인을 거쳐 배포까지 가고, 운영 중 이상이 생기면 자동으로 막고 알린 뒤 복구 작업까지 같은 길로 돌아간다."

부수 목표: 사용자가 이슈, 브랜치, PR, 리뷰(줄 단위 댓글), 머지라는 깃헙 기본 협업 흐름에 익숙해진다.

## 2. 목표 / 비목표 / 실패 조건

### 목표 (1단계)

1. 깃헙 이슈로 요청하면 AI(Claude Code)가 작업해서 PR을 올린다.
2. PR마다 테스트, 보안 검사, AI 리뷰, 위험도 분류가 자동으로 돈다.
3. 위험도 기반 승인 게이트: 위험한 파일을 건드리면 사람의 승인을 반드시 받는다.
4. 머지 후 스테이징 자동 배포, 운영 배포는 사람 승인 후에만 진행한다.
5. 운영 중 이상 감지 → 자동 방어 조치 → 디스코드 알림. 코드 수정이 필요한 문제는 AI가 이슈를 만들어 같은 흐름으로 처리한다.
6. 정기 점검(라이브러리 보안 업데이트 등)이 사람 입력 없이 시작된다.
7. 모든 주요 이벤트가 깃헙 링크와 함께 디스코드로 알림된다.

### 비목표 (1단계에서 하지 않음)

- 슬랙, 지라 연동 → 2단계 **[제안]**
- 디스코드에서 명령으로 작업 요청하는 봇 → 2단계 (선택) **[제안]**
- 리액트 프런트엔드 앱 → 2단계 (같은 파이프라인이 다른 언어에도 적용됨을 보여 주는 용도) **[제안]**
- 휴대폰 본인인증(PASS 등): 사업자 계약과 비용이 필요하다. 이메일 인증으로 대신하되 갈아 끼울 수 있게 만든다. **[판단]**
- 앱 기능의 완성도: 게시판은 시연에 필요한 만큼만 만든다.

### 실패 조건 (동작은 해도 실패로 보는 것)

- **AI나 자동화가 사람 승인 없이 운영 서버를 바꿀 수 있는 경로가 하나라도 있으면** 실패다. **[사용자: "실서버는 AI가 건드리면 안 됨"]**
- 같은 VPS에 있는 **기존 테스트 사이트들에 영향이 가면** 실패다. **[판단, 사용자 상황 기반]**
- 자동 차단이 **사용자 본인이나 관리자를 막아 버리면** 실패다.
- 처음 보는 사람이 흐름을 이해하지 못하면(README와 시연이 부실하면) 포트폴리오로서 실패다.
- 네 개 도구를 한꺼번에 붙이다가 핵심 흐름이 미완성으로 남으면 실패다. 그래서 단계를 나눴다.

## 3. 제약과 현재 상태

- 사용자 경력: PHP, 라라벨, 코드이그나이터 위주. 최근 리액트 + Vite로 쇼핑몰을 만들어 봤다. **[사용자]**
- 깃헙 협업 경험은 적다. 이슈, PR, 브랜치 보호 등의 설정은 설계자가 만들고, 처음에는 사용 방법을 같이 짚는다. **[사용자 상황 + 판단]**
- 계정: 깃헙과 디스코드는 있다. 슬랙과 지라는 없다(2단계에 무료 플랜으로 가입). **[사용자]**
- 서버: 사용자가 임대한 **VPS 1대**가 있다. 도커로 테스트 사이트 몇 개가 올라가 있고, **도메인을 연결해서** 쓰고 있다. **[사용자]**
  - 사양 (2026-11-26 확인): Ubuntu 24.04.4 LTS, CPU 4코어, 메모리 7.8GiB(사용 가능 약 6.3GiB), **스왑 없음**, 디스크 96G 중 65G 여유. Docker 29.7.2, Docker Compose v5.5.0.
  - 80/443은 **`webstack-caddy-1`(caddy:2-alpine) 컨테이너**가 받는다. 서버에 직접 설치된 nginx/apache/caddy는 없다. 인증서는 Caddy가 자동 발급하는 것으로 보인다.
  - 기존 컨테이너: `deskora-web`, `deskora-api`, `deskora-mongo`, `g7-chatbot-php`, `webstack-mysql-1`(mysql:8.4), `webstack-phpmyadmin-1`(127.0.0.1:8081에만 노출), `webstack-caddy-1`. **이 컨테이너들은 이 프로젝트에서 건드리지 않는다.**
- 나중에 다른 언어로 옮겨 갈 가능성을 열어 둔다(AI 시대에 언어 선택이 바뀌는 추세). **[사용자]**
- 예산: VPS가 이미 있으므로 추가 서버 비용은 없다.
- **Claude 비용: 사용자의 Claude Max 구독을 쓴다. API 키는 따로 만들지 않는다.** **[사용자]**
  - 연결 방법: `claude setup-token`으로 구독 연동 토큰을 발급해 저장소 비밀값 `CLAUDE_CODE_OAUTH_TOKEN`에 넣고, Claude Code Action에 `claude_code_oauth_token`으로 전달한다. (claude-code-action 문서와 Claude Code 인증 문서 기준, 2026-11-26 확인)
  - 이 토큰은 **유효기간이 1년**이다. 만료일을 README 운영 메모에 적고, 만료 한 달 전에 디스코드로 알림을 보낸다. **[판단]**
  - 사용량은 사용자가 평소 쓰는 Max 구독 한도에서 함께 차감된다. 그래서 AI 사용을 아낀다. **[판단]**
    - AI 작업은 `@claude` 호출이 있을 때만 돈다.
    - 자동 AI 리뷰는 PR이 **처음 열릴 때 한 번**만 돌고, 이후 커밋마다 다시 돌지 않는다(다시 받고 싶으면 `@claude review` 호출).
    - 운영 감지 → AI 이슈 생성은 같은 오류를 하나로 묶고, 하루 생성 개수에 상한을 둔다(기본값은 빌더가 정함).
  - 봇 신원(GitHub App)으로 PR을 열 때도 Claude 인증은 위 구독 토큰을 그대로 쓴다. GitHub App 토큰은 깃헙 권한용이고, Claude 인증과는 별개다.

## 4. 전체 구조

```
[사람]──이슈 작성(양식)──▶ GitHub Issue ──@claude──▶ Claude Code (GitHub Actions)
                                                         │
                                                         ▼
                                           새 브랜치 + PR 생성
                                                         │
                       ┌─────────────── PR 검사 (자동) ───┴────────────────┐
                       │ 테스트 / 정적분석 / 의존성 취약점 / 비밀키 탐지 /    │
                       │ AI 리뷰 / 위험도 분류(라벨)                         │
                       └──────────────────────┬─────────────────────────────┘
                                              ▼
              [사람] PR 화면에서 리뷰 (줄 단위 댓글 → @claude 재작업 가능)
                         │ 위험 파일 수정 시 CODEOWNERS 승인 필수
                         ▼
                      머지 (main)
                         ▼
                 스테이징 자동 배포 (VPS)
                         ▼
          [사람] 운영 배포 승인 (GitHub Environment 승인)
                         ▼
                   운영 배포 (VPS)

운영 감지 ──▶ 자동 방어 조치 ──▶ 디스코드 알림
           └─ 코드 수정 필요 시 ──▶ AI가 GitHub Issue 생성 ──▶ 위 흐름 그대로

정기 점검 (cron) ──▶ 의존성 업데이트 PR ──▶ 위 흐름 그대로

모든 단계 ──▶ 디스코드 알림 (깃헙 링크 포함)
```

## 5. 구성 요소별 설계

### 5.1 연습용 앱: 간단한 게시판

- **라라벨 API 기반 게시판.** 회원가입, 로그인, 글쓰기, 글 목록이 있다. **[제안]**
  - 이유: 사용자가 익숙한 언어라 앱 만드는 데 시간을 덜 쓴다. 테스트(PHPUnit 또는 Pest)와 보안 검사 도구가 잘 갖춰져 있다. 로그인과 글쓰기가 있어야 비밀번호 대입과 스팸 감지 시나리오를 실제로 재현해서 시연할 수 있다.
- 화면은 최소한으로 둔다. 시연에 필요한 정도의 서버 렌더링 화면(Blade) 또는 아주 단순한 화면이면 충분하다. **[판단]**
- 이메일 인증 코드 발송 기능이 필요하다(5.6 참고).

### 5.2 요청 창구: 깃헙 이슈 **[사용자]**

- 사용자는 **깃헙 이슈와 PR에서** 요청하고 수정 결과를 확인한다. 디스코드에서 한 줄씩 요청하는 방식은 세부 수정을 하나하나 짚기 불편하다는 사용자 판단에 따라 1단계에서 뺐다.
- **이슈 양식(Issue Form)**을 제공한다. 칸은 "무엇을 / 어디서 / 기대 결과 / 완료 체크리스트 / 참고 스크린샷"이다. **[판단]**
- 이슈나 댓글에 `@claude`를 언급하면 Claude Code GitHub Action이 작업을 시작한다.
- PR 리뷰에서 줄 단위 댓글로 `@claude ...`를 남기면 AI가 그 지적대로 다시 고친다.
- 실행 권한: `@claude` 호출은 저장소 소유자(사용자)와 협업자만 할 수 있다. 외부인이 이슈에 `@claude`를 써도 작업이 돌지 않아야 한다. **[판단]**

### 5.3 PR 자동 검사

PR이 생기거나 갱신될 때마다 실행된다.

| 검사 | 도구 예시 (빌더가 최종 선택) | 실패 시 |
|---|---|---|
| 테스트 | PHPUnit / Pest | 머지 차단 |
| 정적 분석 | PHPStan(Larastan) | 머지 차단 |
| 코드 스타일 | Laravel Pint | 머지 차단 또는 자동 수정 (빌더 판단) |
| 의존성 취약점 | `composer audit` | 머지 차단 |
| 비밀키 탐지 | gitleaks 등 | 머지 차단 |
| AI 리뷰 | Claude Code 리뷰 | 의견만 남김, 차단하지 않음 |
| 위험도 분류 | 변경 파일 경로 규칙 + AI 요약 | `risk:high` / `risk:low` 라벨 |

- **언어별 검사는 하나의 분리된 작업(job 또는 재사용 워크플로)으로 묶는다.** 나머지 흐름(알림, 승인, 배포)은 언어와 무관하게 공통으로 쓴다. 나중에 타입스크립트나 파이썬 앱을 붙일 때 이 부분만 교체하면 되게 만든다. **[사용자 요구 → 제안]**

### 5.4 위험도 기반 승인 게이트 **[제안]**

- **고위험 경로** (초안, 빌더가 실제 구조에 맞게 조정):
  - 인증, 권한 관련 코드
  - DB 마이그레이션
  - `.github/` (워크플로 자체 — AI가 자기 권한이나 승인 규칙을 바꾸지 못하게)
  - 배포 설정, 도커 설정
  - 환경 설정, `composer.json`/`composer.lock`
  - 보안 감지와 차단 로직 자체
- 고위험 경로를 건드린 PR:
  - `risk:high` 라벨이 붙는다.
  - 디스코드에 "사람 확인 필요" 알림을 보낸다.
  - CODEOWNERS로 사용자 승인이 필수다.
- 모든 PR에 브랜치 보호를 적용한다: 검사 통과 + 승인 1회 + main 직접 푸시 금지.
- **위험도와 상관없이 모든 PR은 사람이 승인한다. 자동 머지는 하지 않는다.** **[사용자]** 위험도 라벨은 "어디를 더 꼼꼼히 볼지" 알려 주는 표시다. `risk:high` PR은 디스코드 알림에서 별도로 강조하고, PR 설명 맨 위에 AI가 정리한 "고위험 변경 요약(무엇을, 왜, 영향 범위)"과 위험 파일 목록을 붙여 리뷰를 돕는다. **[판단]**
- **AI 작업자는 별도의 봇 신원(GitHub App)으로 PR을 연다.** Claude Code Action의 기본 동작은 브랜치만 올리고 "PR 만들기" 링크를 남기는 것이라, 그대로 두면 사용자가 PR 작성자가 되어 자기 PR을 승인할 수 없다. 봇 신원으로 PR을 열면 사용자가 리뷰어 겸 승인자가 되어 "AI가 작성하고 사람이 승인한다"는 구조가 기록에도 분명히 남는다. **[판단]**
- 사용자가 직접 올린 PR을 어떻게 처리할지는 빌더가 정한다. **[판단]**

### 5.5 배포: 스테이징과 운영 **[제안 + 사용자 서버]**

- 사용자의 기존 VPS에 이 프로젝트용 컨테이너를 **스테이징**과 **운영** 두 벌로 띄운다.
- 접속 주소는 기존 도메인의 하위 도메인 두 개다(예: `staging.<도메인>`, `app.<도메인>`).
- **기존 사이트 격리:** 별도 폴더, 별도 도커 네트워크, 별도 compose 프로젝트로 운영한다. 기존 사이트의 설정과 컨테이너는 건드리지 않는다. 기존 리버스 프록시에 하위 도메인 라우팅을 추가하는 것만 예외로 허용하며, 그 작업은 사용자와 함께 한다. **[판단]**
  - 리버스 프록시는 기존 `webstack-caddy-1`을 쓴다. 이 프로젝트의 스테이징·운영 웹 컨테이너만 Caddy와 공유하는 **전용 외부 도커 네트워크**에 붙이고, Caddyfile에 하위 도메인 블록 두 개를 **추가만** 한 뒤 Caddy 설정을 다시 읽게(reload) 한다. 재시작이 아니라 reload로 해서 기존 사이트가 끊기지 않게 한다. 변경 전 Caddyfile은 백업한다. **[판단]**
  - Caddy가 앱 앞에 있으므로 라라벨에서 **신뢰 프록시(trusted proxy)**를 설정해야 실제 접속자 IP를 알 수 있다. IP 차단은 이 IP를 기준으로 **앱 단(미들웨어)**에서 한다. 서버 방화벽(iptables/ufw, fail2ban)은 기존 사이트에 영향을 줄 수 있으므로 쓰지 않는다. **[판단]**
  - **DB는 기존 `webstack-mysql-1`을 공유하지 않고**, 이 프로젝트 전용 DB 컨테이너를 둔다(스테이징과 운영 DB는 분리). 기존 사이트와 데이터와 장애가 섞이지 않게 하려는 것이다. 메모리 여유(약 6.3GiB)로 충분하다. **[판단]**
  - **서버에서 이미지를 빌드하지 않는다.** 깃헙 Actions에서 도커 이미지를 빌드해 레지스트리(GHCR 등)에 올리고, 서버는 받아서 실행만 한다. 스왑이 없는 서버에서 빌드하다 메모리가 부족해져 기존 사이트까지 영향받는 일을 막기 위해서다. 스왑 추가는 권장 사항으로 사용자에게 안내만 하고, 실행 여부는 사용자가 정한다. **[판단]**
- **배포 전용 계정과 키:** 깃헙이 서버에 접속할 때는 배포 전용 사용자와 SSH 키를 쓴다. 이 키는 이 프로젝트 폴더의 컨테이너를 갱신하는 것만 할 수 있다(서버 관리자 권한 없음, 가능하면 강제 명령(forced command)으로 제한). **[판단]**
- 스테이징: main에 머지되면 자동 배포된다.
- 운영: GitHub Environment `production`에 **필수 승인자(사용자)**를 지정한다. 운영 배포용 비밀키는 이 Environment에만 둔다. 그래서 승인 전에는 어떤 작업도 운영 접속 정보를 볼 수 없다.
- **AI 작업 단계(Claude Code 실행)에는 서버 접속 비밀키를 일절 주지 않는다.**
- 배포 후 상태 확인(health check)이 실패하면 디스코드로 알린다. 자동 롤백 여부는 빌더가 정한다.

### 5.6 운영 감지와 자동 대응 **[사용자 + 제안]**

원칙: **되돌릴 수 있는 방어 조치는 자동, 코드 변경과 운영 배포는 반드시 사람 승인.**

| 감지 | 자동 대응 | 해제 방법 |
|---|---|---|
| 같은 계정 로그인 연속 실패 | **계정 잠금** | 사용자가 **이메일 인증 코드**로 본인 인증하면 해제 **[사용자]** |
| 스팸성 글 폭주 (짧은 시간 다수 등록, 같은 내용·링크 반복) | 해당 계정 **글쓰기 제한**, 의심 글 **숨김**(삭제 아님) | 이메일 본인 인증으로 글쓰기 제한 해제. 숨긴 글은 관리자가 검토 |
| 계정이 없는 공격 (취약 경로 찔러보기, 한 IP의 과도한 요청) | 해당 **IP 일시 차단** | 시간 경과로 자동 해제. 영구 차단은 사람이 결정 **[판단]** |
| 사이트 다운, 응답 지연, SSL 만료 임박, 디스크 부족 | 막을 대상이 없으므로 알림만 | — |
| 500 에러 급증, 같은 오류 반복 | 알림 + **AI가 로그를 분석해 깃헙 이슈 생성** → 4장 흐름으로 처리 | — |

- **예외 목록:** 관리자 계정은 자동 차단 대상에서 뺀다. 가정용 IP는 자주 바뀌므로 **IP 예외에 의존하지 않는다.** IP 일시 차단에 관리자가 걸렸을 때도 풀 수 있는 우회 수단(관리자 전용 해제 경로 또는 서명된 우회 수단 등)을 둔다. 고정 IP가 있으면 IP 예외를 추가로 쓸 수 있다. 우회 수단의 구체적인 방식은 빌더가 정한다. **[판단]**
- **감지와 자동 대응은 스테이징과 운영 모두에서 동작한다.** 공격과 에러 **시연은 스테이징에서** 한다. 운영은 공개 상태로 두되, 가입 시 이메일 인증을 거치게 하고 임계값을 보수적으로 잡아서 실제 스팸·대입 공격과 알림 소음, 메일 발송 한도에 대비한다. **[판단]**
- **운영 로그와 개인정보 보호:** 저장소가 공개이므로, AI에게 넘기는 로그와 AI가 만드는 이슈에는 이메일, IP, 토큰, 설정값이 들어가지 않게 **가림 처리(마스킹)를 먼저** 한다. 이슈에는 원본 로그 대신 오류 요약과 위치(파일·줄)만 남긴다. VPS가 깃헙에 이슈 생성을 요청할 때 쓰는 토큰은 이 저장소의 이슈 생성(또는 작업 시작 신호)만 할 수 있게 권한을 좁힌다. **[판단]**
- 모든 자동 조치는 기록(로그/DB)에 남고, 디스코드로 알린다. 알림에는 무엇을 왜 막았는지와 해제 방법이 들어간다.
- 임계값(몇 번 실패하면 잠글지, 몇 분에 몇 개면 스팸인지)은 빌더가 합리적으로 정하고, 설정 파일로 조정할 수 있게 한다.
- 다운 감지는 앱 내부가 아니라 **외부에서** 확인해야 한다. 앱이 죽으면 스스로 알릴 수 없기 때문이다. 수단(외부 모니터링 서비스, VPS의 별도 컨테이너, 깃헙 cron 등)은 빌더가 정한다.
- AI 이슈 자동 생성은 같은 오류로 이슈가 중복해서 쌓이지 않게 한다.

### 5.7 정기 점검 **[제안]**

- 주기적으로(예: 주 1회) 의존성 보안 업데이트를 확인한다. 필요하면 업데이트 PR을 만든다(Dependabot 또는 AI). 이 PR도 5.3과 5.4를 그대로 거친다(`composer.lock` 변경이므로 고위험으로 분류된다).

### 5.8 디스코드 알림 **[사용자 + 제안]**

- 1단계는 **웹훅** 방식이다(항상 켜져 있는 봇 서버가 필요 없음).
- 모든 알림에 관련 **깃헙 링크**를 넣는다(이슈, PR, 워크플로 실행, 승인 화면). **[사용자]**
- 알림 종류: 이슈 접수 / AI 작업 시작·완료(PR 링크) / 검사 결과와 위험도 / 사람 확인 필요 / 스테이징 배포 완료(주소) / 운영 배포 승인 대기(승인 링크) / 운영 배포 완료·실패 / 감지·자동 차단 발생 / 정기 점검 결과.
- 채널은 최소 두 개로 나누기를 권장한다: 개발 흐름 알림, 운영 감지 알림. 세부 구성은 빌더가 정한다. **[판단]**
- **알림 발송부는 교체 가능하게 만든다.** 디스코드와 슬랙을 설정만 바꿔 갈아 끼울 수 있어야 한다. 2단계 슬랙 연동의 기반이다. **[제안]**

- 짧은 시연 영상 또는 GIF:
  1. 이슈 작성 → AI PR → 검사 → 리뷰 댓글로 재작업 → 승인 → 스테이징 → 운영
  2. 비밀번호 대입 재현 → 계정 잠금 → 디스코드 알림 → 이메일 인증으로 해제
